# 代码提交

## 目标

梳理当前目录或其直接子文件夹中的 Git 仓库全部未提交变更，输出可直接复制的 commit 信息，使用完全相同的信息提交，并推送到各自当前远程分支。

## 工作流程

### 1. 检查仓库

1. 先在当前文件夹定位 Git 仓库根目录并执行 `git status --short`；如果当前文件夹不是 Git 仓库，只检查其直接子文件夹，最多下沉一层，逐个分析其中的 Git 仓库，不递归更深且不扫描上级目录。
2. 检查当前分支、远程仓库和上游分支。
3. 读取已暂存、未暂存和未跟踪文件的差异；结合代码上下文识别实际业务与功能变化，不能只根据文件名概括。
4. 若没有未提交变更，停止提交并直接说明。
5. 若存在删除文件，提交前列出路径并等待用户明确确认删除；未确认不得暂存、提交或推送。

### 2. 处理 application.yml 端口变更

1. 找出所有名为 `application.yml` 的变更文件，逐个检查完整差异。
2. 当某个文件的变更仅为端口号修改时，使用精确文件路径将该文件恢复到 `HEAD`，包括已暂存和未暂存修改，不将其写入提交。
3. 回滚前确认该文件没有端口之外的任何变化；包含其他配置变化时保留整个文件并正常提交。
4. 回滚后重新执行 `git status --short` 和差异检查，确认实际提交范围。

### 3. 生成 commit 信息

1. 第一行使用 `feat: xxxx`，`xxxx` 用一句中文概括本次变更的核心业务目标；用户明确指定其他类型时按用户要求处理。
2. 从第二行开始使用连续编号：`1.xxx`、`2.xxx`、`3.xxx`。
3. 每个细项使用“业务或功能模块:具体改动”的格式，同时说明修改的业务场景和功能点，不能只列文件名、类名或技术动作。
4. 合并重复内容，覆盖全部实际提交变更，不描述未包含在提交中的文件。
5. 将完整信息放在 Markdown 代码块中，确保用户可直接复制，例如：

```text
feat: 完善用户认证流程
1.用户登录接口:增加用户名和密码参数校验，避免无效请求进入认证流程
2.鉴权处理:补充令牌失效判断，统一未授权场景的返回结果
```

### 4. 提交并推送

1. 暂存本次全部有效变更，但不包含已回滚的纯端口 `application.yml`。
2. 使用步骤 3 输出的完整 commit 信息原样执行 `git commit`，标题和编号细项均写入提交正文。
3. 不执行编译、测试、打包、格式化或其他代码修改。
4. 推送当前分支：已有上游分支时执行普通 `git push`；没有上游分支时执行 `git push -u origin <当前分支>`。
5. 禁止强制推送、修改历史、变基或追加到旧提交。
6. 推送失败时保留本地提交，报告原始错误和当前分支，不伪造成功状态。

## 交付格式

最终再次用代码块给出实际使用的完整 commit 信息，并说明提交哈希、当前分支、远程推送结果，以及纯端口 `application.yml` 的回滚情况。不得声称执行了编译或测试。
