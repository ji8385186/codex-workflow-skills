# Bug 修复防回归

用于降低“修复一个 Bug 又引入其他 Bug”的风险。涉及缺陷排查、Bug 修复、修复性重构、用户提供详细设计，或需要分析 Git 未提交代码时启用。

## 本地日志位置与仓库标识

- 日志必须存放在项目目录之外的用户级 Codex 目录：优先使用 `CODEX_HOME`，否则使用 Windows 的 `%USERPROFILE%\.codex`（非 Windows 使用 `~/.codex`）。
- 本技能同时供 Codex、Qoder CLI 与 ZCode 使用（Qoder 侧副本位于 `%USERPROFILE%\.qoder-cn\skills\bug-fix-guardrail\`；ZCode 侧技能位于 `%USERPROFILE%\.zcode\skills\bug-fix-guardrail\`，通过目录联接指向本文件，内容与 Codex 完全一致）。所有 Agent 必须读写上面这同一套 Codex 目录与同一份 `bug-summaries.md`、`bug-fixes.md`；Qoder 不得改用 `~/.qoder-cn` 下的自有目录，ZCode 不得改用 `~/.zcode` 下的自有目录，任何 Agent 都不得另建一份并行记录。
- 项目日志根目录下的 `local-bug-records\project-bug-records-index.md` 是入口索引：计算标识前先读取它，按其中"使用规则"判断项目是否已有 Bug 文档。索引已登记且目录内两个文件齐全时才检索与写入；未登记或记录不完整时视为该项目没有 Bug 文档，跳过记录流程，不自动新建目录或文件，本节的"缺失时按模板创建"仅适用于已登记项目或用户明确要求新建。
- 项目日志路径为 `<Codex目录>/local-bug-records/<仓库唯一标识>/`。确定标识前必须读取 [repository-identity.md](references/repository-identity.md)。
- Git 仓库优先使用本地 Git 配置中的远程 URL（`remote.*.url`）生成标识，不使用当前 Git 根目录作为主标识：优先 `origin`，同一远程有多个 URL 时取规范化结果字典序最小者；没有 `origin` 时取全部远程 URL 规范化结果字典序最小者。
- 将远程 URL 规范化为不含协议、用户名、凭证和查询参数的 `主机[:非默认端口]/仓库路径`，再对 UTF-8 文本计算完整 SHA-256，目录名使用 `remote-<64位小写十六进制哈希>`。因此同一仓库通过 HTTPS/SSH、不同用户名、是否带 `.git` 或位于不同本地目录时仍归档到同一目录；不同 fork 或不同远程地址默认分开。
- 没有可用远程 URL 或当前目录不是 Git 仓库时，才对规范化绝对路径计算 SHA-256，目录名使用 `path-<64位小写十六进制哈希>`。
- `.git` 为文件时，不把文件内容中的 `gitdir` 路径当作远程地址；使用 Git 命令读取其实际 Git 配置中的 `remote.*.url`。不得记录 URL 中的密码、令牌或其他凭证。
- 目录内维护两个文件：
  - `bug-summaries.md`：问题标题、摘要、关键词、状态和详细记录链接，仅用于快速定位。
  - `bug-fixes.md`：问题的现象、复现、根因、设计物料、修复、验证和风险等完整记录。
- 两个文件都不存在时，分别使用 [bug-summary-template.md](references/bug-summary-template.md) 和 [bug-record-template.md](references/bug-record-template.md) 的结构创建。不得覆盖已有文件。
- 禁止在项目内创建 `docs/bug-fixes.md`、`.codex/bug-fixes.md` 或任何同类日志；禁止修改 `.gitignore` 试图解决该问题。日志不应出现在项目 Git 工作树、暂存区或提交中。
- 创建日志目录时只创建上述用户级精确目录，不操作项目根目录或其他目录。
- 旧版本按本地路径生成的目录只读兼容，不删除、不覆盖、不自动合并无法确认归属的记录。若旧记录明确包含相同的规范化远程标识，可按 Bug 编号去重后增量复制到新目录，并在详细记录注明来源；不同旧目录出现相同编号但内容不同的记录时，必须重新分配新唯一编号并保留原始编号，不能丢弃任一记录；后续新记录只写入远程 URL 标识目录。

## 接收的物料与处理模式

先整理用户提供的物料，并区分“用户明确提供”“代码观察结果”和“待确认推断”：

- 问题描述：作为现象、复现条件、期望结果和实际结果的主要依据。
- 详细设计或其他文档：提取相关行为约束、接口契约、数据规则和验收标准；只在与当前问题相关时纳入记录。
- Git 未提交代码：分析工作区和暂存区的变更，判断是否与问题相关、是否已有修复尝试及其回归风险。

根据是否存在历史记录选择一种模式：

- 新建：摘要索引和详细记录均无匹配 Bug，分配新的唯一编号。
- 追加：已定位到历史 Bug，新增本次复现、设计物料、代码分析、验证结果或后续进展，保留原记录。
- 调整：用户提供了更准确的问题描述、详细设计或证据，需要修正标题、摘要、根因、方案、状态或验收标准；保留原结论，并在详细记录中注明调整内容、依据、日期和来源，不得静默覆盖历史信息。

## 开始编码前

1. 按仓库唯一标识读取并确认两个本地日志路径；缺失时按模板创建。已有 `bug-fixes.md` 但没有 `bug-summaries.md` 时，先从详细记录的 Bug 标题和已有字段补建摘要索引，再继续检索。新标识目录没有记录时，再按兼容规则检查旧路径目录。
2. 从用户问题描述、设计物料和未提交代码中提取模块名、类名、方法名、接口、表名、异常信息、业务字段、文件路径和关键词。
3. **先只检索 `bug-summaries.md`**。使用 `rg` 定位标题、摘要、关键词、模块和文件相关的 Bug 编号；不得一开始全文扫描 `bug-fixes.md`。
4. 对摘要中命中的 Bug，依据编号或详细记录链接定位 `bug-fixes.md` 对应章节，再读取详细描述、历史根因、修复方案、风险和后续注意事项。只有摘要缺失、索引不完整或无法建立关联时，才可将详细记录作为兼容性兜底，并在本次完成后补齐索引。
5. 检查当前 Git 状态，至少分析 `git status --short`、变更统计、工作区 diff 和暂存区 diff；必要时限定到受影响路径。记录哪些是用户已有修改，哪些是本次新增修改，禁止重置、覆盖、清理或擅自暂存用户改动。
6. 确认问题现象、复现条件、影响范围、验收标准，并判断历史记录是否适用。若详细设计与现有代码、历史结论冲突，记录冲突和依据，不把推断写成事实。

## 修改与验证

- 优先先增加能复现原问题的失败回归测试，再实施修复。
- 只做解决当前问题所需的最小修改，不顺便重构、升级依赖、改配置或删除无关文件。
- 检查正常路径、空值、边界值、异常路径、重复调用、并发、权限、事务、接口兼容性及数据影响；按项目实际情况选择适用项。
- 先运行受影响模块的测试，再运行项目要求的构建、全量测试、静态检查或 lint。环境不可用时记录未验证项和风险，不得声称已完全修复。
- 检查 `git diff` 和 `git status --short`，确认没有日志文件或无关改动进入项目。
- 用户提供详细设计时，将其转化为记录中的设计依据和验收标准；除非用户明确要求，不因设计文档本身扩展无关代码范围。

## 完成后记录

无论结果是“已修复”“部分修复”“待验证”还是“未解决”，都要同步两个文件，且不得覆盖历史记录：

1. 先在 `bug-fixes.md` 新建、追加或修订详细记录。追加/调整时保留原内容，在同一 Bug 章节增加“补充记录”或“修订记录”，注明日期、处理模式、用户物料摘要、Git 未提交代码分析、变更依据和影响。
2. 再在 `bug-summaries.md` 新建或更新同一 Bug 的唯一摘要条目。摘要应包含可检索的标题、现象概括、模块/关键词、状态、最近更新时间和指向详细章节的链接；调整标题或摘要时同步更新，不得产生重复编号。
3. 新 Bug 编号使用 `BUG-YYYYMMDD-NNN`；`NNN` 必须同时检查摘要和详细文件，按当天现有最大序号递增，避免重复。
4. 完成后先用摘要关键词检索 `bug-summaries.md`，再按编号检索 `bug-fixes.md`，确认索引与详细记录一致、相关历史 Bug 已填写。
5. 不要把密码、令牌、客户隐私或完整生产数据写入日志，只记录必要的脱敏信息。

详细记录至少包含：

- 唯一 Bug 编号、日期、现象和复现步骤；
- 影响范围、根因、修复方案和修改文件；
- 回归风险、相关历史 Bug、测试或构建命令及结果；
- 未验证项、遗留风险和后续注意事项。
